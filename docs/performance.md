# 性能验证

脚本的性能目标是减少重复扫描、无意义写入和不需要的后台活动。源码结构能说明执行方式，实际收益需要浏览器测量；以下流程用于建立可重复的对比。

## 对照条件

使用同一浏览器版本和独立配置，准备四组环境：原生 V2EX、仅 Polish、Polish 加 REP、本脚本。两个参考工具均使用已修复已知签到循环的正常版本，只开启本项目覆盖的功能。

固定主题、起始页、加载页数、图片策略、窗口大小和缓存条件。每组至少重复五次，分别记录冷缓存和热缓存结果，比较中位数。不要将不同预加载页数或异常版本的占用直接作为性能收益。

## 场景与指标

| 场景                   | 观察指标                              | 应检查的异常                     |
| ---------------------- | ------------------------------------- | -------------------------------- |
| 打开主题               | JS 执行时间、长任务、请求数、布局次数 | 启动时多次全页遍历               |
| 追加相同数量的回复     | 主线程耗时、节点数、热评更新时间      | 已有回复重复插入、标签重复渲染   |
| 静置 5 分钟            | CPU、网络、GM 存储写入                | 没有操作仍持续请求或写入         |
| 反复查看预览和用户卡片 | 请求数、堆大小、DOM 节点和监听器      | 缓存不生效、关闭后节点持续增长   |
| 多标签页               | 签到请求、存储事件                    | 成功后重复请求、存储通知回写自身 |
| 上传期间编辑           | 草稿完整性、上传数                    | 完成上传时覆盖新输入、重复上传   |

Chrome DevTools 的 Performance、Performance Monitor、Network 与 Memory 面板可用于采集数据。测试扩展时也要观察其后台 Worker；只看网页分数无法覆盖后台开销。

本脚本不内置持续采样器，避免测量逻辑本身影响日常浏览。若手动修改代码统计 GM 写入，应只统计键名和次数，不输出标签、Client ID、Cookie 或正文。

## 结果记录

记录浏览器与工具版本、主题公开地址、页数、回复数、冷暖缓存、重复次数和中位数。结论需同时说明差异与适用条件。没有完成同机对照前，不应给出 CPU、内存或耗时下降百分比。
