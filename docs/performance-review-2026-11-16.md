# V2EX Lite 性能评估与 v0.1.15 优化结果

评估日期：2026 年 11 月 16 日。基线版本：v0.1.14，提交：52903bb。

v0.1.15 已落地批量折叠、请求队列释放、热评增量更新和构建压缩。正式产物及回归结果见[落地与复测](#v0115-落地与复测)。下文先保留原始评估，便于对照优化依据。

## 结论

当前最值得优化的是长回复折叠的测量与渲染顺序。它在包含较多长回复的页面上，反复触发整页样式计算，收益明显高于单纯压缩文件或拆分模块。

临时样本保留了 30 条折叠回复和 60 条热评：300 条回复一次性渲染时，首屏中位数从 1,388 ms 降至 336 ms；按 100 条加后续两页加载时，累计主线程任务从 1,348 ms 降至 687 ms。

包体也有明确的压缩空间，但本次压缩并未明显改善页面耗时。静置和重复预览中未观察到持续的节点增长。

原始评估仅比较 v0.1.14 与临时性能原型。原型数据不代表正式发布结果，正式版本采用独立复测数据。

## 测量条件

- Windows，AMD Ryzen 7 H 260，16 个逻辑处理器，系统物理内存约 31.3 GiB。
- Chrome 157.0.8103.51，无头模式，禁用 GPU，视口为 1,440 × 900。
- 使用本地 HTTP 服务及此前获取的 V2EX 原生 CSS。未访问真实账户或执行领奖、感谢、屏蔽、上传。
- 压力样本分别包含 100、300 条回复；10% 为长回复，20% 收到感谢，共 80 个不同用户名。
- 默认预加载场景从 100 条开始，再串行追加两页，最终为 300 条。单次 300 条渲染用于放大热点。
- 功能采用现有默认值，但关闭自动签到；除预加载场景外，预加载页数设为 0。GM API 使用内存模拟。
- 每组预热一次，再记录五个新页面的中位数，禁用 HTTP 缓存。进程内存另取三个全新浏览器实例的中位数。
- JS 堆在强制垃圾回收后记录。CPU 使用稳定页面的渲染进程 ProcessTime 增量，采样约 60 秒；“单核等效百分比”不等于任务管理器整机 CPU 百分比。
- 所有数字用于同条件比较，不能直接解释为真实 V2EX 页面的耗时或提升比例。完整样本见 [测量数据](performance-review-2026-11-16.json)。

## 打包体积

| 产物               |  原始体积 | gzip 体积 |
| ------------------ | --------: | --------: |
| 当前正式产物       | 349.3 KiB |  70.5 KiB |
| 仅压缩 JS          | 257.9 KiB |  60.5 KiB |
| 同时压缩 JS 和 CSS | 242.6 KiB |  59.3 KiB |

同时压缩 JS 和 CSS，原始体积减少 30.6%，gzip 体积减少 15.9%。临时构建保留了用户脚本头及第三方许可证。[esbuild 压缩选项](https://esbuild.github.io/api/#minify)可用于缩短正式产物，源码继续保持可读。

按构建元数据，样式约占产物的 35.5%，四种语言文案约占 16.4%，Floating UI 相关代码约占 11.3%。当前未启用 JS 压缩，CSS 作为字符串打包时也未单独压缩。

压缩样本在 300 条回复场景中的首屏为 1,384 ms，当前产物为 1,404 ms；累计主线程任务分别约 1,484、1,474 ms。差异不足以证明速度提升，说明此时的瓶颈主要在运行时渲染。

gzip 数值是同条件压缩比较，不是浏览器实际收到的响应大小，也不是运行内存。本地安装的脚本没有在本次刷新测试中重新请求 GitHub 安装文件。

## 当前加载与主线程开销

| 场景                     | 首次内容绘制 | 累计主线程任务 | 样式计算 | 布局次数 | GC 后 JS 堆 |
| ------------------------ | -----------: | -------------: | -------: | -------: | ----------: |
| 原生 100 条              |       112 ms |          87 ms |     8 ms |        1 |    0.43 MiB |
| Lite 100 条              |       304 ms |         293 ms |   152 ms |       12 |    1.44 MiB |
| 原生 300 条              |       156 ms |         169 ms |    15 ms |        1 |    0.44 MiB |
| Lite 一次性 300 条       |     1,404 ms |       1,474 ms | 1,148 ms |       32 |    1.59 MiB |
| Lite 默认预加载至 300 条 |       336 ms |       1,389 ms |   922 ms |       34 |    1.85 MiB |

“累计主线程任务”不是网络加载总时长。预加载场景能先显示前 100 条，但后续追加仍会产生主线程阻塞。

300 条回复场景中，JS 执行本身约 38 ms，样式计算却超过 1 秒。CPU 采样中最突出的函数是 [折叠模块的 check](https://github.com/ryan961/v2ex-scripts/blob/52903bbca683b08c8efad39fcc076813ca0ccb73/src/folding.js#L21)：读取高度后立即插入折叠容器，下一条回复再读取高度，形成多轮强制样式计算和布局。

仅关闭折叠的诊断样本，样式计算降至约 67 ms、布局降至 2 次。正式优化应保留折叠功能，通过调整执行顺序降低开销。

## 已验证的优化方向

### 批量测量长回复

先收集候选回复并读取高度，再统一修改 DOM。全局帧批处理还可以合并分页追加和 ResizeObserver 触发的检查。

| 指标                      |     当前 | 批处理原型 |
| ------------------------- | -------: | ---------: |
| 一次性 300 条首屏         | 1,388 ms |     336 ms |
| 一次性 300 条主线程任务   | 1,473 ms |     406 ms |
| 一次性 300 条布局次数     |       32 |          3 |
| 预加载至 300 条首屏       |   324 ms |     204 ms |
| 预加载至 300 条主线程任务 | 1,348 ms |     687 ms |
| 预加载至 300 条布局次数   |       34 |          7 |

对应样本的首屏缩短约 75.8%，预加载累计任务减少约 49.0%。这些是压力样本中的结果，不能外推到所有帖子。

两组均保留 30 条折叠回复、60 条完整热评和原有主题。落地时需要验证图片加载后折叠、展开收起、预览、窗口缩放及楼层定位。

### 释放请求队列保留的页面

[请求队列](https://github.com/ryan961/v2ex-scripts/blob/52903bbca683b08c8efad39fcc076813ca0ccb73/src/dom.js#L197)使用最后一个 Promise 作为串行队列的尾部，该 Promise 的兑现值仍是完整 HTMLDocument，导致最近一次抓取的页面继续被持有。

临时改为让队列尾部仅保留完成状态，同时继续把原任务返回给调用方后，预加载场景的文档计数从 2 降至 1，DOM 节点计数从 27,656 降至 23,505，减少约 4,151 个节点。

JS 堆变化很小，收益主要是减少 DOM 文档持有。本项没有明显的加载速度收益，也不意味着它解释了全部预加载内存差异。

### 复用热评克隆节点

[热评渲染](https://github.com/ryan961/v2ex-scripts/blob/52903bbca683b08c8efad39fcc076813ca0ccb73/src/replies.js#L183)在感谢数发生变化时，会移除整个面板，再克隆所有收到感谢的回复。

在有 60 条热评的样本里，仅加入按回复 ID 和感谢数缓存克隆节点，单次感谢数更新的 JS 耗时从约 7.6 ms 降至 3.7 ms，但总主线程任务只从约 39.7 ms 降至 34.0 ms。

因此，此项有收益，但优先级低于折叠。若要进一步改善，应保留面板并只更新变动内容和排序位置，继续保留 REP 的完整回复结构。

## 内存与静置 CPU

| 指标                   | 原生 300 条 | 当前 Lite | 批量折叠原型 |
| ---------------------- | ----------: | --------: | -----------: |
| 主渲染进程工作集       |   100.8 MiB | 175.4 MiB |    163.2 MiB |
| 主渲染进程专用提交     |    52.7 MiB | 113.4 MiB |    101.0 MiB |
| 稳定页面 CPU，单核等效 |       0.12% |     0.19% |        0.18% |

工作集与专用提交取三个全新实例的中位数；CPU 为另一次约 60 秒的采样。进程通过目标页面 ProcessTime 与系统进程 CPU 累计时间匹配，不累加无关或已退出的渲染进程。

JS 堆约 1.6 MiB 不能代表页面总内存。DOM、样式及其他浏览器分配也占用内存；工作集还可能包含共享页。[Chrome 内存说明](https://developer.chrome.com/docs/devtools/memory-problems)区分了操作系统内存和 JS 堆。本次图片是重复的小图，真实大图、GIF 和浏览器扩展可能明显改变占用。

五分钟静置中，Lite 的脚本执行时间没有增加，额外请求和存储写入均为 0，文档保持 1 个、DOM 节点保持 17,130 个。JS 堆仅有约 1 KiB 的测量差异。

连续打开并关闭预览 30 次，GC 后文档保持 1 个、DOM 节点保持 17,130 个、监听器保持 1,633 个。未观察到该场景的持续增长，但这不能证明所有长期使用场景都没有泄漏。

当前主要 CPU 成本集中在初始化、预加载和内容更新。批处理对静置 CPU 的收益很小，没有必要围绕静置状态继续增加复杂调度。

## 代码结构建议

| 优先级       | 调整                              | 收益与边界                                                                                                                                                                                                                                                                                  |
| ------------ | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0           | 将折叠高度测量和 DOM 修改分成批次 | 已验证的主要加载收益；保留现有折叠样式                                                                                                                                                                                                                                                      |
| P1           | 请求队列尾部只保留完成状态        | 改动小，减少完整文档持有                                                                                                                                                                                                                                                                    |
| P1           | 正式构建压缩 JS 和 CSS            | 明确减小包体，保留许可证与可调试源码                                                                                                                                                                                                                                                        |
| P2           | 热评按回复 ID 增量更新            | 降低克隆和重建成本，需保持 REP 展示结构                                                                                                                                                                                                                                                     |
| P2           | 复核追加回复的增强路径            | [直接增强](https://github.com/ryan961/v2ex-scripts/blob/52903bbca683b08c8efad39fcc076813ca0ccb73/src/replies.js#L249)之后，[主观察器](https://github.com/ryan961/v2ex-scripts/blob/52903bbca683b08c8efad39fcc076813ca0ccb73/src/main.js#L110)还会再次遍历；可以合并批次，但收益尚未单独量化 |
| 按数据量决定 | 上传记录分页、状态检查限并发      | 当前记录一次性创建全部行；大量历史时再验证                                                                                                                                                                                                                                                  |

现有原生 DOM 和功能模块划分可以保留。最有价值的结构变化是测量与渲染的边界、请求队列的生命周期，以及重复 DOM 工作的合并。

单纯把 members.js 拆成更多文件，或把四种语言改成多个源文件，在仍打包为单个文件时，不会自动获得运行时收益。Floating UI、输入校验和远程页面清理也不是本次主要热点。

当前已有值得保留的设计：回复 ID 去重、按帧合并变更、忽略自建 UI、用户卡片限量缓存、表情面板延迟创建，以及用户标签每次只显示 50 行。

未经多场景覆盖验证，不宜仅依据首屏未使用的选择器裁剪 Polish 样式；设置、预览、移动布局和动态类名可能用到这些规则。

## 后续验收

- 继续使用相同样本、浏览器和视口比较中位数，保持 30 条折叠回复和 60 条热评。
- 验证首屏、分页追加、楼层定位、图片加载后折叠、预览、草稿及原生回复操作。
- 验证串行请求、失败重试及账号校验没有被削弱。
- 保留所有第三方许可证；压缩产物需要完成完整功能和样式回归。
- 重复预览并静置五分钟后，检查文档、DOM、监听器和 GC 后堆大小是否持续增长。

未完成真实 Tampermonkey 后台、Firefox、复杂图片页面、超大量标签和上传记录、长期多标签页，以及正常 Polish + REP 的同机对照。因此，本报告不宣称 Lite 相比上游工具快多少。

## v0.1.15 落地与复测

正式版本完成四项调整：

- 长回复在同一动画帧中先统一测量，再插入折叠容器。图片加载和窗口变化共用这条路径，退出页面时取消待处理任务。
- 串行请求队列只保留完成状态，调用方仍收到原始解析文档，原有失败处理和账号校验保持有效。
- 热评保留面板及未变动的回复节点，只替换变化的内容和调整顺序。已有观察器使内容或标签变化的缓存失效，继续保留完整回复。
- 正式构建压缩 JS 和 CSS，保留脚本元数据与全部第三方许可证，并增加 250 KiB 的产物体积检查。

现有模块划分继续保留。追加回复增强路径、上传历史分页等未单独量化的结构调整留待出现足够收益时处理。

复测采用前述机器、浏览器和样本，各场景预热后取五次中位数。旧版与正式新版交替运行，降低执行顺序的影响。以下数据与上文原型属于不同轮次，应在本表内比较。

正式产物为 249,129 字节，比旧版减少 30.4%。预加载样本减少 4,151 个保留节点。一次性 300 条回复的 GC 后 JS 堆中位数由约 1.58 MiB 降至 1.33 MiB；本轮没有重新测量操作系统进程工作集，因此不将 JS 堆的变化表述为总内存降幅。

自动测试共 65 项通过，新增覆盖测量与 DOM 修改顺序、合并调度、退出清理、请求串行与失败恢复、热评节点复用及内容失效，以及构建许可证和体积。浏览器回归核对了预览、200 楼后的回复操作、分页和草稿、浮动回复框、标签更新、设置返回与快捷按钮。主要组件的抽样计算样式与旧版一致，功能操作使用本地模拟接口。

连续打开并关闭预览 30 次，文档保持 1 个、DOM 节点保持 17,130 个、监听器保持 1,633 个。随后静置五分钟，没有新增脚本执行、请求或存储写入，文档和节点计数保持不变。本轮未观察到这些场景的持续增长。

复测原始数据保存在测量 JSON 的 releaseValidation 字段，包含产物 SHA-256、全部样本和静置检查点。真实网络、Tampermonkey 后台、Firefox、复杂图片和长期多标签页仍未覆盖；性能数字只用于同条件比较。
